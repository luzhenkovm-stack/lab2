# Лабораторная работа №2 — Интерфейсы. Репозиторий. JSON

Решение на C# / .NET 8, SQLite и ASP.NET Core Minimal API. Все три части собраны в одном проекте.

## Запуск

Требуется установленный .NET 8 SDK.

```bash
dotnet restore
dotnet run --urls http://localhost:5000
```

При первом запуске автоматически создаётся файл `lab02.db` и таблицы `Books` и `User`.
Откройте `http://localhost:5000/` для проверки доступности API.

Для запуска демонстрации интерфейсов:

```bash
dotnet run -- --interfaces-demo
```

## Часть 1 — интерфейсы

Код находится в `Interfaces/BasicInterfaces.cs`:
- `IMovable` и `Point`;
- `IDrawable`, `Circle`, `Rectangle`, `DrawingService.DrawAll`;
- `IShape`, `I3DShape`, `Cube`, `ShapeInfoPrinter.PrintShapeInfo`;
- пример «толстого» `IDevice`, затем разделение на `IPrinter`, `IScanner`, `IFax`;
- `IPayable`, `CreditCard`, `Cash`, `PaymentProcessor.ProcessPayment`;
- `ILogger`, `ConsoleLogger`, `FileLogger`, `WorkService.DoWork`.

## Часть 2 — Repository

Предметная область: каталог книг. Сущность `Book` содержит `Id`, `Title`, `Author`, `Price`. В `AppDbContext` настроены таблицы SQLite. Реализованы `IRepository<T>`, `IAsyncRepository<T>`, `GenericRepository<T>`, специализированный `IBookRepository` и `BookRepository`, а также `IUnitOfWork` / `UnitOfWork`.

HTTP-маршруты книг: `GET/POST /books`, `GET/PUT/DELETE /books/{id}`, `GET /books/by-author/{author}`.

## Часть 3 — JSON REST API пользователей

Таблица `User`: `Id` (PK), `Login` (уникальный индекс), `PassHash`.

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/user` | Создать пользователя |
| GET | `/user/{id}` | Получить пользователя |
| PUT | `/user/{id}` | Изменить пользователя |
| DELETE | `/user/{id}` | Удалить пользователя |

Все запросы и ответы — JSON. `PassHash` намеренно не возвращается в ответах API. API ожидает уже вычисленный хеш, а не открытый пароль. Для реального приложения следует вычислять хеш на сервере с Argon2id/bcrypt/PBKDF2 и никогда не принимать от клиента произвольный `PassHash` как доказательство аутентификации; здесь формат соответствует заданию лабораторной.

### Примеры запросов (curl)

Создать пользователя:

```bash
curl -i -X POST http://localhost:5000/user \
  -H "Content-Type: application/json" \
  -d '{"login":"example_user","passHash":"$2b$12$example_hash_value"}'
```

Получить пользователя (например, с Id=1):

```bash
curl -i http://localhost:5000/user/1
```

Обновить:

```bash
curl -i -X PUT http://localhost:5000/user/1 \
  -H "Content-Type: application/json" \
  -d '{"login":"new_login","passHash":"$2b$12$new_example_hash"}'
```

Удалить:

```bash
curl -i -X DELETE http://localhost:5000/user/1
```

Повторный логин вернёт HTTP 409 Conflict; некорректные данные — HTTP 400; отсутствующий пользователь — HTTP 404.

## Контрольные вопросы

1. **Что такое интерфейс?** Контракт, который задаёт набор доступных членов (в этой работе — методов), которые обязуется реализовать класс или структура.
2. **Можно ли создать объект интерфейса напрямую?** Нет. Нельзя создать экземпляр самого интерфейса; можно объявить переменную интерфейсного типа и присвоить ей объект реализующего его класса.
3. **Зачем нужен полиморфизм интерфейсов?** Чтобы работать с разными объектами через общий контракт, не связывая вызывающий код с конкретными классами.
4. **Чем интерфейсы отличаются от абстрактных классов?** Класс может реализовать несколько интерфейсов, но наследоваться только от одного базового класса. Абстрактный класс может хранить состояние, конструкторы и реализацию; интерфейс в первую очередь задаёт контракт и не предназначен для хранения состояния экземпляра.
5. **Что такое ISP?** Принцип разделения интерфейсов: клиент не должен зависеть от методов, которые он не использует. Лучше несколько узких специализированных интерфейсов, чем один универсальный «толстый».
6. **Примеры из жизни.** Платёжные способы (`IPayable`), устройства печати/сканирования (`IPrinter`/`IScanner`), способы логирования (`ILogger`), перемещаемые объекты (`IMovable`).

## ER-схема

```text
+-------------------------+       +-------------------------+
|          User           |       |          Books          |
+-------------------------+       +-------------------------+
| PK Id       INTEGER     |       | PK Id       INTEGER     |
| UQ Login    TEXT        |       |    Title    TEXT        |
|    PassHash TEXT        |       |    Author   TEXT        |
+-------------------------+       |    Price    DECIMAL     |
                                  +-------------------------+
```

Таблицы независимы, поэтому связей (FK) между ними нет.

## Выводы

Интерфейсы позволяют отделить контракт от реализации и обеспечивают полиморфизм. Разделение интерфейсов по ISP делает классы проще и избавляет от пустых или искусственных методов. Паттерн Repository отделяет бизнес-код от конкретного способа хранения данных, упрощает тестирование и замену СУБД. GenericRepository сокращает дублирование CRUD-кода, специализированный репозиторий содержит предметные запросы, а Unit of Work координирует изменения через общий контекст. REST API с JSON обеспечивает стандартное сетевое взаимодействие с данными; уникальный индекс и валидация защищают от повторяющихся логинов и некорректных записей.
